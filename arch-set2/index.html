Q1

アプリケーションで命名規約を採用することが、なぜそれほど重要なのですか？

  • Aパターン（標準）を正規化するため。
  • Bリファレンスアーキテクチャを強制するため。
  • C他のすべての選択肢が正しい。
  • D各モジュールの性質を明らかにするため。

正解：C

命名規約の目的は「パターンの正規化」「リファレンスアーキテクチャの強制」「各モジュールの性質の明示」の3つで、いずれも正しい説明です。

Q2

Architecture Canvas を使うべき理由として当てはまらないものはどれですか？

  • A再利用可能なサービスの抽象化を促進する。
  • Bサービスの分離と疎結合を促進する。
  • Cライフサイクルの独立性を最適化する。
  • D変更の影響を最小化する。

正解：B

Architecture Canvas（多層フレームワーク）の利点として公式に挙げられるのは「再利用可能サービスの正しい抽象化」「ライフサイクル独立性の最適化」「変更影響の最小化」の3つです。「分離と疎結合」は一般的な SOA 用語であり、Canvas の利点として列挙されている文言ではありません。

Q3

OutSystems において、Foundation・Core・End-User の各モジュールを持つアプリケーションは、次のうちどれですか？

  • AEnd-User アプリケーション。
  • BFoundation アプリケーション。
  • CCore アプリケーション。

正解：A

アプリケーション内のモジュールのうち最上位レイヤーが、そのアプリケーションのレイヤーを決定します。End-User モジュールを含むので End-User アプリケーションです。

Q4

組み込みテーマをクローンした場合の結果はどれですか？

  • Aベーステーマの新しいバージョンの恩恵を受けられなくなる。
  • Bテーマの更新によってシステムが不安定になり、性能が悪化する可能性がある。
  • C余分な CSS のインポートやリソースのために性能が低下する。
  • Dベーステーマに導入される更新と利点をすべて受け取れる。

正解：A

クローンは元テーマから切り離されたコピーになるため、以降ベーステーマ（OutSystems UI）側の改善・修正を自動では受け取れません。性能低下や不安定化は直接の結果ではありません。

Q5

命名規約の採用にはいくつかの利点があります。次のうち、命名規約を採用する利点で「ない」ものはどれですか？

  • Aエラーコードを回避する。
  • Bリファレンスアーキテクチャを強制する。
  • C各モジュールの性質を明らかにする。
  • Dパターンを正規化する。

正解：A

命名規約は各モジュールの目的を理解しやすくするものであり、エラーコードを回避するものではありません。

Q6

正しいアプリケーション構成のルールはどれですか？

  • Aモジュールを正しいレイヤーに置き、アプリケーションを正しいレイヤーに置く。
  • Bモジュールを正しいレイヤーに置き、アプリケーションを正しいレイヤーに置き、異なるアプリオーナーを混在させない。
  • Cモジュールを正しいレイヤーに置き、アプリケーションを正しいレイヤーに置き、異なるアプリオーナーを混在させず、異なるスポンサーを混在させない。
  • Dモジュールを正しいレイヤーに置き、アプリケーションを正しいレイヤーに置き、異なるアプリオーナーを混在させず、各プロジェクトのスポンサーを定義する。

正解：C

アプリケーション構成ルールは4つです：①モジュールを正しいレイヤーへ、②アプリを正しいレイヤーへ、③オーナーを混在させない、④スポンサーを混在させない。オーナー／スポンサーが異なる要素を同じアプリに入れると、ライフサイクルと責任が絡み合います。

Q7

スタイルガイドを事前に定義する利点を表しているのはどれですか？

  • A性能と保守性を向上させる。
  • B開発フェーズを高速化する。
  • Cアプリとスタイルガイドを本番環境にデプロイできるようにする。
  • Dセキュリティとスケーラビリティ。

正解：A

必要なリソースだけを読み込むようにすることで性能が向上し、保守性の面では、すべてのアプリが初日からスタイルガイドを容易に採用できます。

Q8

Foundation 層のモジュールに含まれるデータ要素はどれですか？

  • ACore エンティティ（読み取り専用で公開）。
  • Bエンティティに対する CRUD アクション。
  • CUI の状態を保存するエンティティ。
  • D非 Core エンティティ。

正解：D

非 Core エンティティはビジネスに依存しない（business-agnostic）ものであり、Foundation モジュールで定義されます。Core エンティティやそのラッパーは Core 層に置きます。

Q9

Core 層に適用すべき推奨事項はどれですか？

  • ACore モジュールはビジネスロジックを持つべきではない。
  • BCore モジュールはテスト目的のフロントエンド画面を持つべきである。
  • CCore モジュールは Core エンティティを持つべきではない。
  • DCore モジュールは公開の読み取り専用エンティティを持つべきである。

正解：D

エンティティを読み取り専用（Public + Read Only）で公開することで、利用側モジュールがレコードを直接作成・更新・削除できないことが保証されます。

Q10

誤ったアプリケーション構成の結果はどうなりますか？

  • Aアプリケーションのライフサイクルの依存を減らし、影響を減らす。
  • Bアプリケーションのライフサイクルの独立性を妨げ、不要な影響を追加する。
  • Cアプリケーションのライフサイクルの依存を減らす。
  • Dアプリケーションのライフサイクルの独立性を高め、不要な影響を追加しない。

正解：B

構成を誤ると、本来無関係な機能が同じアプリのライフサイクルに縛られ、デプロイや変更のたびに不要な影響が生じます。

Q11

次のうち、Architecture Canvas を採用する利点はどれですか？

  • Aアーキテクチャ設計に対する体系的なアプローチである。
  • Bより速いアーキテクチャ設計である。
  • Cアーキテクチャの問題を自動的に発見・修正する方法である。
  • Dビジネスユーザーの協働と理解を促進する。

正解：A

体系的なアプローチを用いることで、結果としてアーキテクチャ設計プロセスを速めることができます。「速さ」自体や「自動修正」は Canvas の利点として挙げられていません。

Q12

Architecture Canvas は多層フレームワークです。このフレームワークの利点で「ない」ものはどれですか？

  • Aライフサイクルの独立性を最適化する。
  • B性能ボトルネックの可能性を特定する。
  • C変更の影響を最小化する。
  • D再利用可能なサービスの正しい抽象化を促進する。

正解：B

Architecture Canvas は実装の詳細には踏み込みません。性能面で注意が必要なコンポーネントを見つける助けにはなりますが、それはアーキテクチャ設計そのものの一部ではありません。

Q13

Cold Cache と Batch Sync を組み合わせた統合パターンの利点は何ですか？

  • A唯一の利点は、ソースシステムへの影響が少ないことである。
  • Bソースシステムへの影響が少ない、より単純な API、OutSystems 内でのデータ突合（クロスチェック）が可能、Core サービスの利用者が同期の影響を受けない。
  • Cソースシステムへの影響が大きい、OutSystems 内でのデータ突合が可能、Core サービスの利用者が同期の影響を受ける。
  • Dソースシステムへの影響が少ない、より堅牢な API、OutSystems 内での突合が不要、Core サービスの利用者が同期の影響を受けない。

正解：B

データを定期的に OutSystems 側へ取り込み（Batch Sync）ローカルに保持する（Cold Cache）ことで、外部システムへのアクセス頻度が下がり、API は単純化され、ローカルデータとの突合が可能になり、利用者は同期処理を意識せずに済みます。

Q14

OutSystems 11 では、画面遷移先（Screen destination）は次のように扱われます：

  • A弱い参照であるため、サイド参照があってもアーキテクチャ違反を示さない。
  • B強い依存であるため、サイド参照があればアーキテクチャ違反を示す。
  • C強い依存であるため、サイド参照があってもアーキテクチャ違反を示さない。
  • D弱い参照であるため、サイド参照があればアーキテクチャ違反を示す。

正解：A

O11 では画面参照はすべて弱い参照（実行時に解決される）として扱われ、End-User モジュール間の画面遷移によるサイド参照は違反になりません。強い参照はアクション・エンティティ・ブロックなど、コンパイル時に依存するものです。

Q15

Calculation Engine（_Eng）モジュールを作成する正当な理由を表しているのはどれですか？

  • Aエンティティと CRUD 編集を持つ概念を支えるため。
  • B複数の Business Logic モジュールに実装されたさまざまな複雑なロジックを抽象化するため。
  • C複雑な計算（例：保険シミュレータ）を支えるため。
  • DCore Widget モジュールからの再利用可能なアクションを支えるため。

正解：C

_Eng は、保険料の試算やスコアリングなど、それ自体が独立した複雑な計算ロジックを分離して保持するための Core 層モジュールです。エンティティ中心なら _CS、汎用ロジックなら _BL を使います。

Q16

テーマとレイアウトはアプリケーションの重要な要素です。次のうち、これらの要素を定義する場所として正しいのはどれですか？

  • AMyApp_Th モジュール（End-User 層）。
  • BMyApp_CS モジュール（Foundation 層）。
  • CMyApp_BL（Foundation 層）。
  • DMyApp_MTh（Foundation 層）。

正解：D

テーマ（_Th / _MTh）は Foundation 層に置きます。命名規約に「M」が付いていることは、これがモバイル用テーマモジュールであることを意味します。

Q17

カスタムテーマで共通のメニューとログインを持つ構成タイプはどれですか？

  • Aポータル
  • B独立アプリとポータル
  • C独立アプリ
  • Dイントラネット

正解：A

ポータル構成は、共通テーマ・共通メニュー・共通ログインを持ち、複数の機能を1つの統合された入り口から提供します。独立アプリ構成では各アプリが独自のメニューとテーマを持ちます。

Q18

次のうち、組み込みスタイルガイドをクローンすることを選ぶべきシナリオはどれですか？

  • A組み込みスタイルガイドは OutSystems UI の一部なのでカスタマイズできない。
  • Bベーステーマへの小さなカスタマイズをアプリのテーマ内で行うべきとき。
  • C既存のテーマに大規模な変更を加えたいとき。
  • D既存のどのテーマも活用できず、大規模な変更が必要なとき。

正解：C

最も活用できるテーマとテンプレートを選び、そこから始めます。小さな変更ならアプリテーマの上書きで十分、既存テーマに大幅な変更を入れたいならクローン、どのテーマも使えないならゼロからのカスタムスタイルガイドです。

Q19

次のうち、カスタムスタイルガイドを実装すべきシナリオはどれですか？

  • Aアプリケーションが既存のどのテーマの恩恵も受けられないとき。元のテンプレートのブロックやアクションを活用して開発を加速するため、利用可能な最も複雑なテンプレートをクローンして実装すべきである。
  • Bアプリケーションが独立したデプロイと、他のアプリケーションとの低い相互依存を必要とするとき。
  • C常に。すべてのプロジェクト／アプリケーションは独自のカスタムスタイルガイドを持つべきである。
  • Dアプリケーションが既存のどのテーマの恩恵も受けられないとき。開始に必要な最小限の構造だけを含むため、可能な限り最も基本的なテンプレートから始めて実装すべきである。

正解：D

カスタムスタイルガイドは、既存テーマを活用できない場合にのみ作成し、最小構成のテンプレートから出発します。複雑なテンプレートは不要な資産を抱え込むため出発点に向きません。

Q20

OutSystems において、Core アプリケーションに含められるのは…

  • AFoundation モジュールのみ。
  • BEnd-User モジュールと Core モジュール。
  • CEnd-User、Core、Foundation モジュール。
  • DFoundation モジュールと Core モジュール。

正解：D

アプリのレイヤーは最上位モジュールで決まるため、Core アプリには Core と Foundation のモジュールを含められますが、End-User モジュールは含められません（含めると End-User アプリになります）。同様に Foundation アプリには Foundation モジュールしか含まれません。

Q21

OutSystems における「コールドキャッシュ（cold cache）」とは何ですか？

  • A頻繁にアクセスされるデータをメモリに保持してアプリケーションの性能を向上させる技法。
  • B頻繁には変化しないデータをキャッシュするために使われる仕組み。
  • COutSystems プラットフォームのすべてのモジュールが非アクティブな状態。
  • DOutSystems のモジュールやアプリケーションが再起動され、キャッシュされたすべてのデータを再読込する必要がある状況。

正解：B

コールドキャッシュは、外部システムのデータのうち更新頻度の低いものを OutSystems 側のエンティティに複製しておく統合パターンです。メモリ上のキャッシュではなく、ローカルDBへの永続的なコピーです。

Q22

アーキテクチャ設計プロセスには3つのステップがあります。次のうち、そのステップで「ない」ものはどれですか？

  • ADisclose（開示）
  • BAssemble（組み立て）
  • CPlan（計画）
  • DOrganize（整理）

正解：C

計画は重要ですが、アーキテクチャ設計プロセスのステップではありません。3つのステップは Disclose、Organize、Assemble です。

Q23

Core モジュールに上方参照（upward reference）を見つけたと仮定します。この問題はどのように修正できますか？

  • A消費されている要素を見つけて中間レイヤーへ移動し、影響を減らす。
  • B消費されている要素を見つけて下位レイヤーへ移動する。
  • C消費されているモジュール全体を下位レイヤーへ移動する。
  • D消費されている要素を見つけて同じレイヤーの別のモジュールへ移動する。

正解：B

上方参照とは、下位レイヤーのモジュールが上位レイヤーの要素を消費している状態です。消費されている要素だけを（モジュール全体ではなく）下位レイヤーへ移せば、依存の向きが正常化します。

Q24

End-User モジュール間に弱いサイド参照があるとします。アーキテクチャ違反を避けるためにその参照を取り除く最善の方法は何ですか？

  • A消費されている要素（遷移先を除く）を特定し、再利用可能な Core／Foundation モジュールへ移動する。
  • Bこのようなシナリオでは、参照を避けるために常に消費される要素をプロデューサーモジュールからコンシューマーモジュールへ移動すべきである。
  • C画面遷移先を外部 URL に置き換え、アクションを REST API 経由で消費する。
  • DEnd-User モジュール間の弱いサイド参照は許容されているため、その参照を取り除く必要はない。

正解：D

End-User 間で禁止されるのは「強い」サイド参照です。画面遷移などによる弱いサイド参照は許容されるので、対処は不要です。

Q25

アプリケーション構成の検証ルールに関して、次のうち正しい文はどれですか？

  • Aアプリケーションのオーナーは混在させるべきではないが、スポンサーの混在はリリースに直接の影響を与えない。
  • BFoundation 層のアプリケーションは End-User 層のアプリケーションを参照できる。
  • C共通のモジュールとサービスは、他のアプリケーションから参照できる別のアプリケーションに分離すべきである。
  • Dモジュールの検証ルールをすべて守れば、アプリケーション構成は健全で、保守とデプロイが容易になる。

正解：C

再利用性が鍵であり、参照の問題を避ける助けになります。スポンサーの混在も避けるべきルールであり、Foundation アプリが End-User アプリを参照するのは上方参照、モジュールルールだけではアプリ構成の健全性は保証されません。

Q26

SSL Pinning はモバイルアプリケーションにおけるセキュリティのベストプラクティスです。SSL Pinning について「誤り」であるものはどれですか？

  • ASSL Pinning または HTTP Public Key Pinning（HPKP）は、中間者攻撃（man-in-the-middle）の軽減に役立つ。
  • Bクライアント側で動作し、モバイルアプリに事前に同梱された公開鍵のハッシュとサーバー証明書を照合する検証を追加する。
  • C上記はすべて正しい。
  • DSSL Pinning は、公開鍵をコードにハードコードすることを意味するものではない。

正解：D

SSL Pinning は、信頼する公開鍵（のハッシュ）をアプリに埋め込み（ハードコード／同梱し）、接続先証明書と照合する手法です。したがって「ハードコードを意味しない」という文が誤りです。

Q27

OutSystems でモジュール間の要素を移動するとき、特に注意して慎重に扱うべき要素はどれですか？

  • AAction・Structure・Block のようなデータの永続性を持たない要素。永続的でないため、移動の過程で意図せず削除される可能性がある。
  • BEntity のようなデータの永続性を持つ要素。Entity を移動しても移動されるのは論理定義だけであり、物理的には別のデータベーステーブルになる。
  • CTimer・Site Property・Role のような設定可能な要素のみ。これらは開発環境と本番環境で異なるデータ永続性を持つ唯一の要素である。
  • D特に注意すべき要素はない。モジュール間で移動されるすべての要素は整合性を保つ。

正解：B

Entity を別モジュールへ移動すると新しい物理テーブルが作られ、既存データは自動では移りません。データ移行の計画が必要です。

Q28

アプリケーションをリファクタリングする際は、新しい要素を追加する前にアプリケーションを本番環境にデプロイすることが重要です。正しい選択肢を選んでください：

  • Aこの文は正しい。システムを平準化するため、新しい機能を追加する前にアプリケーションを本番環境にデプロイする必要がある。
  • Bこの文は誤り。新しい機能を追加する前に、テスト環境に変更をデプロイするだけでよい。
  • Cこの文は誤り。リファクタリング時は、新しい要素を追加する前にアプリケーションを他の環境にデプロイする必要はない。
  • Dこの文は正しい。将来動作しない可能性のある機能で開発者を過負荷にしないよう、新しい機能を追加する前にアプリケーションを本番環境にデプロイする必要がある。

正解：D

リファクタリングと新機能開発を混ぜないのが原則です。まずリファクタリング結果を本番まで到達させて安定させてから、次の機能追加に進みます。

Q29

次のうち、Architecture Canvas を採用する利点を表しているものはどれですか？

  • ACanvas は、アーキテクチャ原則に従いそれを修正する自動的な方法を提供する。
  • BCanvas は、検証ツールに支えられた、アーキテクチャ設計への体系的なアプローチを提供する。
  • CCanvas は、検証を必要としない、より速いアーキテクチャ設計を提供する。
  • DCanvas は、ビジネスユーザーの協働と理解を容易に促進する方法を提供する。

正解：B

Canvas は設計の「体系的なアプローチ」であり、Discovery や AI Mentor Studio といった検証ツールが設計の妥当性確認を支えます。自動修正やビジネスユーザーの理解促進は利点として挙げられていません。

Q30

Architecture Canvas のどのレイヤーで、最も高い再利用率が期待できますか？

  • ACore 層。
  • BFoundation 層。
  • CEnd-User 層。

正解：B

Foundation 層の要素はビジネスに依存しない（business-agnostic）ものであり、Core のビジネス要素を持たない前提です。そのため、どのアプリからも横断的に再利用されます。

  • Bリスクを減らす
  • C計画立案を支援する
  • Dコストを削減する

正解：A

「貧弱なサービス抽象化」は、明確に定義されたアーキテクチャが「ない」場合に生じる結果です。

Q32

OutSystems では、無関係な概念を同じモジュールにまとめることは推奨されていますか？

  • Aはい。循環参照を避け、生成コードのフットプリントを減らすため。
  • Bいいえ。両方の概念を必要とする利用者に不要な複雑さを加えるため。
  • Cいいえ。概念のライフサイクルの独立性を妨げ、利用者に不要な影響を加えるため。
  • Dはい。参照数が減り、デプロイが簡素化されるため。

正解：C

無関係な概念を同居させると、一方の変更がもう一方の利用者にまで影響します。Assemble 原則「異なるライフサイクルの概念は分ける」の通り、分離が推奨です。

Q33

次の文を考えてください：「OutSystems 11 では、Foundation 層のモジュールでビジネス関連の画面を使うことが推奨される。アーキテクチャ検証ルールを何も破らないからである。」次のうち正しいものはどれですか？

正解：A

検証ルール上は違反にならなくても、Foundation 層はビジネスに依存しない層であるべきです。ビジネス関連の画面（一覧・登録など）は End-User 層に置きます。

Q34

次の文を完成させてください：上方違反（upward violation）は、__________ を明確に示している。

上方参照は、下位層のモジュールが上位層のサービスに依存している状態であり、本来共有されるべきサービスが下位層へ正しく切り出されていない（分離されていない）ことを示します。

Q35

次のうち、モジュールの検証ルールで「ない」ものはどれですか？

モジュール間の（必要な）下方参照は、健全なモジュラーアーキテクチャの実現に不可欠です。禁止されるのは上方参照・循環参照・End-User 間の（強い）サイド参照です。

Q36

次のうち、Assemble（組み立て）の原則はどれですか？

正解：A

ライフサイクルの異なる概念は別モジュールに置くべきです。これによりアプリのデプロイが容易になり、作業を独立して進められます。「開示する」は Disclose ステップの内容です。

Q37

AI Mentor Studio（旧 Architecture Dashboard）について、次のうち「誤り」である文はどれですか？

Q38

アーキテクチャ設計を支えるために多層フレームワークを持つことが、なぜそれほど重要なのですか？

Q39

次のうち、サービス構成レベル（levels of service composition）に含まれないものはどれですか？

  • BIntegration Services
  • CFoundation Services

SOA のサービス構成レベルは、Integration Services（外部システムのラッパー）→ Core Services（ビジネスルールとエンティティ）→ External API（外部への公開）の3つです。Foundation Services という区分はありません。

Q41

次のうち、良いアーキテクチャを持つことの利点はどれですか？

Q42

Integration Services サービスレベルの目的を最もよく表しているのはどれですか？

  • Aこのレベルは外部プロデューサーの技術的ラッパーであり、データ構造を正規化し、統合の複雑さ（エラーからの回復、外部システムでの認証など）を抽象化する。

Q43

Q44

  • AEnd-User モジュールの内部に共有サービスが多すぎる。

Q46

次のうち、モバイルアプリケーションの同期（Synchronization）のベストプラクティスで「ない」ものはどれですか？

  • A同期の粒度を確保する：ネットワーク断による絶え間ない再試行に備え、作業を繰り返さないようにする。エンティティ単位で、チャンクに分けて増分同期する。
  • B必要なときだけ同期する。セッション開始時：サマリデータをローカルストレージへ同期／プロセス開始時：プロセスの詳細をローカルストレージへ同期／プロセス（トランザクション）終了時：サーバーへ書き戻す。
  • C厳密に必要なときだけ同期し、すべての画面やオンラインイベントで同期しない。
  • D小さく軽量な更新を保証するため、Entity Bulk Operation（一括操作）を使用しない。
  • E関連するデータのみ同期する。差分（デルタ）のみ同期する：制御用タイムスタンプを使う。1つのトランザクションでの長い同期を避ける。

正解：D

公式ドキュメント「Handling Optimized Complex Synchronization on Mobile Devices」では、ベストプラクティスとして「Use Entity Bulk Operations (built-in)」が明記されています。一括操作はむしろ同期を効率化するための推奨手法であり、「使用しない」は誤りです。他の4つはいずれも公式の同期ベストプラクティスです。※元の問題集ではこの問題は「[EM ANÁLISE]（審査中）」とマークされ、正解が E に設定されていましたが、E の内容はすべて正しいベストプラクティスであるため、本問では D を正解としています。

Q47

アーキテクチャへの配慮が欠けていても「起きない」ものはどれですか？

  • A管理不能な依存関係：システム同士が分離されていない。あるシステムの更新や置き換えが、他のシステムにカスケード（雪だるま式）の影響を及ぼす。
  • B貧弱なサービス抽象化：ビジネス概念が正しく分離されておらず、ビジネスルールが異なるシステムに散らばりがちで、コードの再利用がほとんど、あるいはまったくない。
  • C技術的負債：AI Mentor が、循環依存やサイド依存といったアーキテクチャの技術的負債を増加させる。
  • D硬直的で動きの遅いレガシーシステム：レガシーシステムをビジネスの変化に適応させるのが難しい場合がある。複雑で硬直したシステムの変更には長い時間がかかりうる。

正解：C

AI Mentor Studio は技術的負債を「検出して可視化」するツールであり、負債を「増やす」ものではありません。他の3つはアーキテクチャへの配慮が欠けた場合の典型的な結果です。
